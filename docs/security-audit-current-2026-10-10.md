# Audit actuel — 10 octobre 2026

État audité : commit `aa59c8f`, avec Vibe Code Security Reviewer. Ce rapport remplace les conclusions des deux audits précédents pour cet état du dépôt.

## Résultat

**Quatre défauts reproduits dans une base de test isolée à partir du schéma complet versionné.** Les contrôles ont utilisé le rôle SQL `authenticated`, des identités et données fictives, puis un rollback. La base de test a été supprimée ; aucune donnée personnelle consultée et aucune modification de la base de développement ou de production.

La suppression des exports Word/PDF/JSON et des tables de configuration élimine le précédent chemin d'exfiltration par URL de génération. `schema.sql` s'installe désormais en entier, avec tables exceptionnelles séparées, politiques et GRANT explicites. La protection des rôles et les restrictions de planning restent validées par les tests existants.

Les quatre constats sont indépendants de l'édition du rôle : les probes réussissent avec des rôles SQL protégés et sans élévation de privilèges. Ils sont confirmés sur le schéma versionné installé en test, pas sur le déploiement de production.

## Vérifications et périmètre

- `npm run test:db-tests` : installation complète, permissions de profils, contraintes, création d'opérations, planning, initiateurs et rôle RH validés.
- Probes supplémentaires : [security-audit-probes.sql](security-audit-probes.sql), exécutées après les mêmes fixtures Auth/profils que `scripts/test-schema.cjs`. Un runner temporaire dérivé du script a chargé ces probes dans sa base dédiée puis a été supprimé. Ces probes diagnostiquent les défauts : leur succès n'est pas un indicateur de sécurité et elles ne doivent pas devenir des tests CI « verts » sans inversion des attentes après correction.
- `npm audit --omit=dev --json` : zéro vulnérabilité connue signalée dans les dépendances de production.
- Inspection du catalogue local en lecture seule : toujours uniquement `app_documents`, avec quatre politiques inconditionnelles pour authenticated. Cela confirme un décalage avec le schéma testé ; ce catalogue ne prouve pas l'application des corrections relationnelles dans l'environnement utilisé.
- Recherche des usages dangereux de HTML/JavaScript et des marqueurs de clés privilégiées dans les sources/configurations parcourues : aucun résultat. Ce contrôle ne couvre pas exhaustivement l'historique Git, les secrets déployés ou les services externes.

Les inscriptions restent ouvertes sans confirmation dans la configuration Supabase locale. Leur ouverture en production et l'exposition réseau ne sont pas vérifiées : un compte nouvellement créé pourrait accéder aux chemins ci-dessus si cette configuration est déployée. Aucun test HTTP authentifié contre un système réel ni audit de production n'a été effectué.

La CI appelle désormais indirectement les tests SQL via `npm test`. Elle doit néanmoins fournir le conteneur PostgreSQL attendu : le workflow actuel ne contient pas d'étape créant ce conteneur. Le succès local ne prouve donc pas un succès CI.

Priorité : protéger les visas et les coefficients RH, restreindre les signatures, formaliser les transitions RH, puis vérifier que les permissions corrigées sont réellement appliquées au déploiement. Aucun correctif applicatif effectué pendant cet audit.
