# Nouvelle analyse de sécurité — 10 octobre 2026

Cette analyse remplace les conclusions du premier audit pour l'état actuel du dépôt. Workflow Vibe Code Security Reviewer : authentification, droits API/SQL, données sensibles et opérations métier. Aucun correctif applicatif ni modification de la base de développement.

## Résultat et validation

**L'élévation de privilèges par édition du profil est corrigée dans les migrations testées.** La migration `20261010190000_protect_user_roles.sql` retire les anciennes politiques et protège rôle, identité et email avec un trigger. Les nouvelles politiques restrictives et les triggers limitent également la création d'opérations, l'édition des plannings et les interventions d'autrui. Les politiques restrictives s'appliquent par AND : leur coexistence avec des politiques permissives `true` ne constitue donc pas, à elle seule, un contournement.

`node scripts/test-user-roles.cjs` : succès. Le script crée puis supprime sa propre base de test et vérifie les profils, créations, plannings, interventions, initiateurs et rôle RH, ainsi que la réapplication des migrations. Ce sont des fixtures SQL minimales ; ce résultat ne valide ni la restauration du schéma complet ni les droits réellement déployés.

`npm audit --omit=dev --json` : zéro vulnérabilité signalée.

Inspection en lecture seule du catalogue local : la base `postgres` contient toujours uniquement `public.app_documents`, avec droits CRUD et politiques inconditionnelles pour `authenticated`. Les nouvelles migrations relationnelles n'y sont donc pas validées en situation réelle. Aucun contenu personnel n'a été lu. La configuration et les permissions de production ne sont pas connues.

L'accès global à l'ancien `app_documents` est confirmé par ses permissions locales, mais le client actuel utilise les repositories relationnels : cette table ancienne n'est pas une preuve que les nouveaux chemins applicatifs fonctionnent localement.

## Écarts de déploiement et de vérification

Le schéma de base définit encore `exceptional_operation_participants` et `exceptional_interventions`, tandis que les migrations et le client attendent des tables séparées par famille. Les fixtures de tests créent ces tables elles-mêmes. Le succès des tests ne prouve donc pas qu'une installation neuve à partir des fichiers versionnés fonctionne. Vérifier le schéma effectivement installé et sa procédure de création avant de déclarer les corrections déployées.

La CI exécute les tests unitaires et le build, mais pas `test:db-user-roles`. Ajouter ces contrôles SQL à une CI disposant d'une base isolée et valider la restauration complète afin d'éviter une régression d'autorisation silencieuse.

Priorité : vérifier le déploiement réel, protéger les visas et les paramètres RH, isoler les signatures, puis encadrer les transitions RH. Les rôles et plusieurs écritures de planning sont désormais protégés dans le périmètre testé ; l'application entière n'est pas pour autant validée.

Contrôles positifs : rôles issus d'un profil SQL protégé, fonctions SECURITY DEFINER à search_path fixe et droits restreints, politiques restrictives, tests SQL négatifs, requêtes SDK structurées. Aucune clé privilégiée repérée dans les sources et configurations parcourues ; contrôle non exhaustif de l'historique et des secrets déployés.
